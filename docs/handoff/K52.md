# K52: fast lifting mode (opt-in `pipeline.liftMode: "fast"`)

## Numeric header

ns per retired guest instruction (median of 5 rotating fresh-instance samples, 30 timed host updates each,
~13M guest instructions per update) and dynamic wasm operators per guest instruction (k41 counter, JSPI).
"current" is the default exact emitter (`exact`); `liftPreset: "fast"` (exact-fast) is within noise of it.
Native is the same C (vm, calls) or scalar C equivalents of the assembly kernels (flags, memory) compiled
directly to wasm; its denominator is the guest instruction count of the same work (guest RDTSC).

Speed-up over current: vm 3.0x, flags 2.2x, memory 9.0x (JSPI) / 11x (Asyncify), calls 3.1x.
Lifted C: -51% bytes (vm 872,130 to 422,968; flags/memory/calls ~780 KB to ~384 KB); lifted object -51%;
lifted-TU compile 2.4-2.8x faster (vm 5.5 s to 1.9 s, others ~4.0 s to ~1.6 s, same flags, one machine).

others ~1,443,000 to ~1,295,000 B). The default build's lifted C is byte-identical to base `072cc0c`.

flags (2.0x), memory (2.2-2.7x) and vm (3.3-3.5x, borderline); the call-dense fixture is 4.4x.

## What changed

- `tools/x86/lift64_fast.h` (new): the fast AMD64 emitter, opt-in via `--lift-mode fast`. See
  [pipeline.md "Fast lifting mode (K52)"](../pipeline.md#fast-lifting-mode-k52-opt-in) for the full shape.
  Brief items: (a) whole-function C, GPRs/flags/clock in locals, spilled at calls/exits only; (b) entries only
  at function start, loop headers and post-call sites, everything else takes the slow path (one interpreted
  instruction then re-entry); (c) flat direct memory: window mask (default) or a committed-range compare, plus
  static-RSP-delta stack slots; checked page-table form kept as `liftFast.memory: "off"`; (d) quantum polls at
  function entries and loop headers only, inline when provably non-suspending. Added beyond the brief because
  the measurements demanded it: emission-level inlining of small direct callees (biggest win on call-dense
  code), fused compare+branch predicates, and recovery of clang/MSVC relative jump tables (without it the VM
  switch fell to the slow path: 49.9M slow-path instructions in 80 updates).
- `tools/x86/lift64.h`: dispatches to the fast emitter for functions of at most 4096 instructions; the fast
  operand forms in `l64_pointer`/atomic emission are guarded by `l64_fast`, so exact output is unchanged.
- `tools/x86/x86tool.c`: `--lift-mode exact|fast`; measurement knobs `--fast-{resume,fuse,memory,entries,
  quantum,stack,inline}`; `fastFunctions`/`fastInlined` in stats (fast mode only).
- `tools/build/chunks.mjs`: `pipeline.liftMode`, `pipeline.liftFast` knobs, `BGT_LIFT_MODE` override. Absent
  (or `exact`) leaves the policy object, and therefore every cache key, unchanged.
- `platforms/x86/x86_rt.c`, `x86_guest.h`, `x86_lift64.h`: `x86_fast_quantum`, `x86_fast_exec` (deferred
  cooperation via `x86_fast_inline`), `x86_fast_yield` (driver and interpreter loop cooperate after a fast
  unwind; `x86_native_ready` refuses while it is set), `x86_fast_lookup` + exported `x86_lifted_generation`
  and `x86_pending_import`, `x86_set_quantum_probe`; helpers `xf_ptr`, `XF_RANGE`, `XF_MASK`, `xf_cond`,
  `xf_shift`, `xf_busy`, `xf_lookup`. Exact paths only gained the `x86_fast_yield` checks (never set by them).
- `platforms/win32/w32_thread.c`, `w32_core.c`: `w32_thread_quantum_probe` (one thread and the frame cap
  not reached after committing the quantum), registered at boot.
- Bench: `tools/bench/k52-fixture.mjs`, `k52.test.ts`, `k52.config.ts`. Tests: `tests/unit/lift-fast.test.ts`.
  Docs: `docs/pipeline.md`.

## Per-change gains (ablations)

Each column removes one feature from full fast mode. Cell = ablation ns / fast ns, JSPI / Asyncify; above 1.0
means the feature helps by that factor. Raw samples: scratch `k52/time-final.json` (listed under Evidence).

| removed feature | vm | flags | memory | calls |
|---|---:|---:|---:|---:|
| (d) sparse quantum (poll every block instead) | 5.20 / 5.45 | 3.62 / 3.45 | 3.18 / 3.88 | 2.14 / 2.16 |
| (c) direct memory (page-table checked instead) | 1.76 / 1.70 | 1.02 / 1.02 | 3.71 / 4.36 | 1.51 / 1.62 |
| (c) window mask (committed-range compare instead) | 1.44 / 1.44 | 1.00 / 1.02 | 1.42 / 1.81 | 1.01 / 1.00 |
| (c) static-delta stack slots (with mask) | 0.98 / 0.98 | 1.01 / 1.09 | 1.00 / 1.13 | 1.00 / 1.00 |
| (b) entry restriction (every block an entry instead) | 1.39 / 1.52 | 1.04 / 1.04 | 1.04 / 1.29 | 1.00 / 1.01 |
| emission-level inlining of small callees | 1.30 / 1.34 | 1.15 / 1.11 | 3.35 / 3.79 | 1.26 / 1.34 |
| fused compare+branch predicates | 1.11 / 1.08 | 1.30 / 1.31 | **0.73 / 0.92** | 1.02 / 1.01 |
| post-call resume entries | 1.00 / 0.95 | 0.99 / 1.22 | 1.07 / 1.27 | 0.99 / 1.03 |

(a) Registers in locals: the exact AMD64 emitter already keeps registers in per-region locals, so there is no
clean knob. The whole-function form is what makes (b)-(d) and inlining possible. The stack-slot form matters
with `range`: memory 5.4x to 3.8x and calls 5.6x to 4.5x of native. Fusion makes the memory fixture slower;
that is unexplained (both forms fold to one compare in C) and listed below.

## Correctness

- All four fixtures x all twelve variants x both suspension modes print exactly the exact-mode line (first
  outer iteration checksum and its guest RDTSC instruction count, e.g. `k52 vm checksum aa982e3b insns
  5114629`), report no faults or interpreted instructions, and produce the same 20 per-update API-trace hashes
  as exact mode. Native checksums match for flags/memory/calls (the VM native adapter differs by design).
- `tests/unit/lift-fast.test.ts` (10 with JSPI): policy plumbing; exact output identical with
  `--lift-mode exact`; fast entry set; fusion; inlining; relative-table switch; production runtime against the
  interpreter (registers, RIP, RAM, retirement) for 100-deep recursion with quantum transfers at four budgets
  (mask/range x inline on/off), indirect calls, generic CPUID, a patched qword table, callbacks, park/rewind
  (real Asyncify and JSPI) and nonlocal transfer. EFLAGS are not compared (dead across calls per the ABI).
- Pipeline examples, exact vs fast: see the gates section.

## Not done / follow-ups

- **Game measurement** (coordinator): `BGT_LIFT_MODE=fast` builds MMX8 without editing `game.json`.
- Remaining gap: 64-bit register locals keep 32-bit results with `i64.and 0xffffffff`; guest stack stores
  stay real stores (no frame promotion); XMM registers stay in `X` (SSE-heavy code will be slower than these
  integer fixtures suggest); REP string ops run through the generic semantic core.
- Deferred (non-leaf) imports, for example GL calls, still unwind all native frames; the post-call entries make
  the resume cheap, but JSPI builds could call non-transferring imports inline. With several guest threads every
  quantum (2M instructions) unwinds.
- Fusion regression on the memory fixture (0.74x) needs a look at the generated wasm.
- i386 ignores `liftMode` (exact emitter only).

## Coordinator decisions needed

1. Default memory form for fast mode: `mask` (fastest; a wild guest pointer aliases guest memory or traps past
   the committed end instead of an access-violation stop) vs `range` (exact-style stop, 1.0-1.45x slower).
   I chose `mask` because the policy is performance first; it never touches host memory.
2. Fast mode assumes Win64 ABI behaviour: flags dead across calls/returns, callee-saved registers preserved.
   Hand-written assembly that violates this needs `liftMode: "exact"` (per game or via an override).
3. Whether to make fast mode the pipeline default after the game measurement (left as opt-in here).
