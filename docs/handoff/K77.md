## JSPI design

A new test-only handshake enables a returnable outer Win64 dispatch on actual JSPI wasm (no Asyncify download, module swap, or replay of the path from boot). At the tail of SwapBuffers a parked marker tells the profile to return rather than call the suspending import. The register CPU, return result, thunk/guest stack, scheduler state and any outer continuation phase live in wasm state. The wrapper returns normally through the real JSPI promising export, leaving **no wasm frame parked**; the host marks a logical yield for diagnostics/pacing. Next update runs post-boundary pumps, finishes the Win64 guest ABI return, and resumes dispatch. Some idle scheduler and exit boundaries likewise return. Existing artifacts need rebuilding for the handshake. Ordinary play and Asyncify do not enable it. C stacks in native callbacks, init, generic API transport waits and some budget waits cannot be reconstructed and still use JSPI; snapshot explicitly refuses any such live stack. Do not claim arbitrary JSPI support.

`debug2.log`: x64-gl-fbo remains on nonreturnable startup boundaries until update 40 (native WebGL2), where checkpoint succeeds (~69 ms); debugger run subsequently passed its continuous/restored suffix test on that backend. At update 1, x64-threads is live but parked at a nonreturnable yield; its first observed returnable boundary (2) has already exited. Preserve the existing live-thread assertion; localize and implement a resumable budget/scheduling boundary or add a scheduler fixture that demonstrably parks live, retaining a rejection test for the uncovered case. Replace hardcoded frame 40 test setup with a bounded first-portable-present search or known fixture contract and verify on WebGPU, both modes. Audit remaining control paths in `platforms/win32/w32_core.c` (including nested callbacks, cap and profiling) and compare ordinary JSPI vs new handshake guest-visible time/results/pixels before accepting.

## Capture cost

Capture does not hash or recompile the artifact; integrity hashing is loader-only. Base `snapshot()` sparsifies with a JS scan of the entire wasm reservation, then may replay the entire GPU prefix if packed depth/stencil or legacy targets require an earlier cut. The same-size restore only has a compact base and up to two residual updates. On the CC0 benchmark, the 2,049-frame GPU journal gives seconds of capture vs ~14 ms restore; exact attribution between replay, memory and copies is pending stage measurements. Do not infer the exact private 242.5 s split from this.

- On multi-memory engines, load-time test instrumentation rewrites wasm stores and bulk copy/fill using interned helpers that mark the touched pages in a private second 64 KiB wasm memory. Host destination writes are enumerated separately. Capture copies only possibly dirty 64 KiB pages (including zero overwrites), relative to the freshly instantiated module image, with no full-reservation scan. Memory growth, original module indices, and old zero-baseline checkpoint input remain supported. Engines without multi-memory still scan exactly. Write-set is cumulative relative to module load, not incremental since the previous capture; dense states cost their actual dirty bytes. Needs dedicated tracking unit cases for cross-page writes, bulk/fill, sign/widths, zero over active data, restore/mutation, and fallback/unsupported opcode. Audit the wasm offset/LEB scanner and host write sites; validate production tree shaking.
- GPU materialization now rolls the journal after 128 frames on successful safe compactions and batches replay fences. Failed provenance still fails closed, with increasing retry thresholds. This shifts GPU work into occasional opted-in lead-in updates; benchmark total lead-in wall time as well as synchronous capture. Needs full GPU parity/provenance/renderer-loss regressions; audit render overlap/resize and byte limits. Stage fields in snapshot stats separate wasm capture, host capture, GPU materialization and replay. Avoid generating full runtime diagnostics just to check device reset count.
