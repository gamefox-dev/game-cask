## 1. Q135: guest-visible GPU limits differ by backend

**Cause (r30, confirmed).** The guest reads GL_MAX_UNIFORM_BLOCK_SIZE = §13.6 offset 52, which K51 made the device's
value: ANGLE Metal 16384, SwiftShader and WebGPU 65536. MMX8 lays out its uniforms from it, so its timeline diverged
on ANGLE from update 50. The audit found two more device-derived values (below); everything else is constant.

**Ruling applied.** New `HostConfig.gpuLimits` / manifest `gpu.limits` / `RuntimeOptions.gpuLimits` /
`?gpulimits=`: `"portable"` (default) reports `min(portable, device)` from `GPU_PORTABLE_LIMITS`
(`bgt/runtime/abi.ts`); `"device"` reports the device's value (K51/K62 behaviour). Never more than the device can do.
The portable table is the minimum across the supported backends/devices measured here, never below GL 3.3:

## 2. Q139: `step(n)` != n x `step(1)` on WebGPU

**Cause (confirmed).** `step()` awaited the render queue and host I/O before each update but the renderer only after
the chunk (`renderer.finish()`). A WebGPU shader/readback result resolves asynchronously outside host I/O, so every
update of a chunk polled the same 0 and the result became visible only after the chunk. Between `step(1)` calls,
`finish()` (onSubmittedWorkDone) let it arrive.

**Fix (`bgt/runtime/runtime.ts`).** `stepRequestWait()` before each stepped update: `host.transportWait()` (the K70
`Requests.awaited()` request the previous update polled unresolved, raced with pending host I/O), bounded by a 10 s
hang guard (`STEP_REQUEST_WAIT_MS`, counted). `pageLoop()` adds `stepRequestWaits`, `stepRequestWaitMs`,
`stepRequestWaitTimeouts`. `?iowait=0` / `ioWait: false` also disables this wait (A/B). No ABI change; ABI.md test API
and `docs/performance.md` updated.

**Measurement** (`tests/e2e/step-chunks.spec.ts`, x64-gl-programs, 250 updates, rows every 25 updates: frame,
guest presents, guest virtual time, state hash; `K73 step-chunks` console line):

| run (WebGPU Metal) | step(25) x 10 at update 250 | 25 x step(1) x 10 at update 250 | identical rows |
|---|---|---|---|
| before (`BGT_K73_IOWAIT=0`) | 0 presents, 0 us, `fa204c6f`, programs not done | 130, 2,166,710 us, `58caaa68` | no (fails) |
| after, Asyncify | 130, 2,166,710 us, `58caaa68` (96 waits, 25.8 ms, 0 timeouts) | same | 10 / 10 |

## 3. Coordinator addition: collector catches network-level request failures; capped allowances

`tests/e2e/fixtures.ts` `collector` (kit and port specs) + pure rules in `tests/support/browser-collector.ts`:
- Playwright `requestfailed` (aborted, DNS, connection refused/reset, blocked) is now a failure, as
  `requestFailures` (`${errorText} ${method} ${url}`). Before: only console errors, page errors and HTTP >= 400
  (Chromium happens to log a console line for connection-refused, but not for an aborted request: that passed).
- `collector.allowRequestFailure(re | { pattern, max })` is the only allowlist for them; `allow()` never masks one.
- `collector.allow({ pattern, max })` (and the same form in `allowRequestFailure`): at most `max` matches across the
  test, every further one fails; plain RegExp entries stay unbounded (unchanged).
- A cancellation (net::ERR_ABORTED / NS_BINDING_ABORTED / cancelled) of a request issued before the main frame's last
  navigation is logged under `navigationAborts`, never a failure. Measured: Chromium/Playwright emits no
  `requestfailed` for such requests at all (probe `scratch-K73/navprobe`), so this is defensive for other engines.
- Tests: `tests/unit/browser-collector.test.ts` (5: refused reported, allow() does not mask, caps across lists and
  over-cap fallthrough, request-failure caps and malformed entries, cancellation texts of three engines);
  `tests/e2e/collector.spec.ts` (7, WebGL2 project: refused, aborted and allow()-masked requests fail the test
  (`test.fail()`), an allowed intentional abort passes and is logged, cap passes at max and fails at max + 1, an
  in-flight request at navigation does not fail). With the pre-K73 fixture: aborted, allow()-masked, both cap cases
  and the allowRequestFailure case fail (`e2e-neg-collector.log`: 5 failed, 2 passed).
- `.claude/skills/browser-validation/SKILL.md` documents the rules.

**V30 note (varying limit differs by backend: WebGPU 106 vs WebGL2 87).** Covered: those are
MAX_VERTEX_OUTPUT_COMPONENTS on WebGPU (102 + 4) and MAX_VARYING_COMPONENTS on SwiftShader (87); see the table
