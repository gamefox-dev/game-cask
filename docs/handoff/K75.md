# K75: fast-mode guest-state divergences (captured EFLAGS, instruction clock), fast oracle in CI

Branch `kit/lane/K75`, worktree `/Volumes/CaskWork/lanes/K75`, `BGT_E2E_PORT=5390`. No game data, no network, no
installs. Evidence: `/Volumes/CaskWork/lanes/scratch-K75/` (`logs/oracle-*.txt|log`, `logs/strict*.txt`, `k52/`).

## 1. Localization

**x64-cpp, x64-heap (EFLAGS in CONTEXT records).** The profile stores `X.flags` in exactly one place,
`w64_context_save` (`platforms/win32/w32_x64.c`), reached from RtlCaptureContext and from `unwind_exception` without
an initial context (RaiseException, RtlUnwindEx outside a dispatch, `w32_heap_no_memory` from HeapCreate/HeapAlloc/
HeapReAlloc under `HEAP_GENERATE_EXCEPTIONS`). Fast mode treats calls as flag-dead (`l64f_flag_io`: CALL/RET read
nothing), so the last flag writer before such a call was elided (`xl_alu(..., mask 0)`) and `XF_SPILL`/`xf_enter`
published a stale `flags` local:
- x64-cpp `0x01001020` (CRT startup): `call 0x010017e0; lea rsi,[rbp-0x40]; mov rcx,rsi; call [RtlCaptureContext]`.
  No writer between the two calls: the captured EFLAGS are the ones the *callee* returned with; fast mode neither
  computed them in the callee (its RET was flag-dead) nor reloaded them in the caller.
- x64-cpp `0x0100573a` (libgcc `_Unwind_RaiseException`, inlined into 8 callers): `xor edx,edx; mov r8d,1;
  call [RaiseException]`; the xor's ZF|PF were elided.
- x64-heap: the HeapAlloc call sites of the `HEAP_GENERATE_EXCEPTIONS` heap: the six exception records' EFlags.

**x64-time (QPC 1 µs late).** Guest time is `virtual_units + debt(X.frame_insns)` (4000 units/µs). The interpreter
cooperates when a quantum's 2000001st instruction starts (`++frame_insns > 2000000`), charges 2000000 and then runs
that instruction uncounted (or, on a thread transfer, re-executes it later counted in the next quantum, X.tsc counting
it twice). Fast mode polls later (loop headers, function entries, after REP generics) with `frame_insns` = F >
2000000, and `x86_cooperate` charged `min(F, 2000000)` and reset the counter: the overshoot F-2000001 was dropped every
fast quantum, so guest time fell behind; at frame 13 three copies of a QPC value read 0x44bda instead of 0x44bdb.

## 2. Fixes

- **Observed EFLAGS** (vK75 extended it to unknown callees, see "vK75 review fixes"; `tools/x86/lift64_fast.h`, default; `liftFast.flags: "abi"` / `--fast-flags abi` keeps the K52
  rule for measurement). A second, interprocedural flag liveness (`l64f_obs_io`) next to the K52 one: a call or tail
  jump to an EFLAGS-storing import (`tools/x86/lift64_eflags.h`, the list above) or to code that is no analyzed
  function reads every flag; every profile call passes flags through; a direct call/tail call reads them when the
  callee observes its entry flags; a RET reads them when a caller observes the flags its callee returns with (the
  caller then reloads `flags=X.flags` after the call, also after an inlined tail call). `l64f_observe` computes the
  two function sets once per lift, over the whole module (worklist fixed point, independent of the chunk selection,
  binary-search function index); emission uses the union of both livenesses. Generic instructions keep their
  conservative *local* read but do not observe across calls: a first version that let them (and every import)
  observe made the K52 fixtures 1-29% slower (hot kernels became exact-exit because an RDTSC generic followed the
  inlined call, and an import in the memory fixture's loop paid full flags). Stats: `fastFlagObservers`,
  `fastFlagExactExits`, `fastFlagUnknownCallees`, `fastFlagAnalysis_cpu_ms` (per chunk; aggregated in `chunks.mjs`).
- **Callbacks restore EFLAGS** (`x86_callback64`, all modes): a profile call is flag-transparent even when it runs guest
  callbacks (Windows leaves EFLAGS unspecified after a call, so this is a valid choice; exact and interpreted builds
  change identically).
- **Quantum charge with carry** (`x86_quantum_charge` in `x86_guest.h`, `cooperate(fast)` in `x86_rt.c`): fast callers
  are charged exactly what the interpreter would have charged up to their poll (2000000 per started quantum) and keep
  the rest in `frame_insns`; on a thread transfer the trigger instruction's re-execution is accounted for (+1 carried,
  +1 X.tsc). `x86_fast_quantum` returns without cooperating at exactly 2000000 (the interpreter has not reached its
  quantum yet). The Win32 probe uses the same charge. Interpreter/exact callers are unchanged (they always arrive at
  2000001). No tolerance was needed: the clock matches exactly (see the lift-fast clock assertions below).

## 4. vK72b review items (coordinator addendum)

1. **Every thread's CPU in fast builds once a second thread runs: measured, not adopted.** With the fixes above,
   `BGT_ORACLE_STATE=cpu,flags,memory` (every thread) diverges in `cpu` at x64-time frame 1; a narrower variant
   (running thread + threads blocked in an API, skipping only quantum-preempted ready threads) diverges at x64-time
   frame 1 and x64-threads frame 0; memory and trace stay identical in all of them. Cause: a fast quantum yields at a
   loop header/function entry, not at the interpreter's instruction, so preemption points and the interleaving differ
   (exact positions need per-block polls: K52 ablation 2-5x slower). The default stays as vK72 (live-thread count after
   the second thread); `x86_state.c` documents the measurement. Flags stay out of the fast default (13): they are
   exact where the profile stores them, not at an arbitrary frame boundary inside an API (an intermediate version
   that made every import observe passed parts 15 on x64-cpp and x64-heap, but cost up to 10% on the K52 memory
   fixture, whose loop calls an import).
2. **Last-frame memory hash:** `guest(h, last)` gets an explicit last-frame flag; the index no longer counts
   x64-smoke's 20 startup calls (`memoryHashDue`, unit-tested).

   under `port/` (policy test added).
4. **Docs:** the state hash lives in `platforms/x86/x86_state.c` (pipeline.md, K72.md fixed).
5. **Unmapped pages:** the memory part now also hashes, in flat builds, any unmapped page inside the committed window

## vK75 review fixes

Rulings: per-thread fast CPU compare stays relaxed (follow-up below); callbacks restoring EFLAGS accepted.

1. **HIGH, probe vs cap accounting** (`w32_thread_quantum_probe`, `w32_clock_quantum_fits(units, carry)`): the probe
   now adds the carried instructions exactly as `w32_clock_check_cap`'s sync does after the inline quantum. Test
   (`oracle-fast.test.ts`, single thread, `timeModel.instructionCap: 2000001`, every frame ends at the cap): no
   fault, more than 10 cap hits and the guest's 13 output lines equal to the interpreter's, Asyncify and JSPI; with
   the old probe it aborts on Asyncify with `x86: suspension requested inside a generated native step` (checked by
   reverting the probe). Found on the way: the oracle read `metrics().cap_hits`, which does not exist (it is
   `guest_time.cap_hits`), so its "frame ended at the cap" relaxation never applied; fixed.
2. **MEDIUM, soundness of flag materialization.** Lazy materialization inside the profile would need the last flag
   writer's operands at every call site (stores on every call, and every `X.flags` reader in the runtime taught to
   materialize); not done. Instead the conservative rule (pipeline.md "Flags"): unknown callees (indirect calls,
   unresolved indirect jumps, other guest modules' imports via `fastGuestDlls`, non-functions) read every flag and
   define them (the caller reloads `X.flags` after the call), and every address-taken function (entry, export,
   relocated pointer, LEA/MOV of its start: `func_t.taken` in the analyzer plus an operand scan in `l64f_observe`)
   returns exact flags. Test: a pointer call to the profile right after `cmp`, and a pointer call to an address-taken
   function returning ZF|PF directly followed by a profile call: both captures equal the interpreter's and the
   architectural values, inline 0/48 x both shapes, and are lost with `--fast-flags abi`. Cost: table above.
   **Still not covered** (exact mode covers it): a function whose address the analyzer cannot see being taken
   (pointer stored in data without a relocation, or computed), called through that pointer, when the caller's next
   instruction reaches an EFLAGS-storing API before any flag writer. **Other consumers** (documented in
   pipeline.md): GetThreadContext/SetThreadContext fail (`ERROR_NOT_SUPPORTED`); AddVectoredExceptionHandler fails and
   hardware exceptions are not dispatched; jmp buffers hold no EFLAGS; RtlRestoreContext restores `CONTEXT.EFlags`.
3. **LOW, `testCorrupt` port check:** `refuseTestCorruptPort` compares real paths (symlinked aliases of `port/` or of
   the game directory are refused); unit-tested with both symlink forms.

**Follow-up (ruling 1):** localize the fast multi-thread CPU differences per thread and register (x64-time frame 1,
x64-threads frame 0, memory identical): which registers differ in quantum-preempted vs API-blocked threads, and
whether a yield-point-independent subset (callee-saved registers of blocked threads, say) is comparable.
