## Baseline measurement before implementation

Environment: shared macOS arm64 host, Node 24.19.0, Zig 0.13.0, Binaryen 132; serial execution. The
workload built as normal Win64 C at -O2: 81 functions, 1,845 specialized and 12 generic lifted instructions,
five unresolved indirect jumps. The initial dev.19 emitter already had register-local GPR emission, flag
liveness, merged affine memory spans, inline-safe ALU/memory policies, and bounded native call regions; these
were measured as existing behavior, not K34 changes.

| Mode | Median 300-update ms | Samples (seven, sorted) | Guest clock | Lifted/interpreted oracle |
|---|---:|---|---:|---|
| Asyncify | 11.679 | 11.065, 11.550, 11.658, 11.679, 11.945, 12.126, 12.961 | 4,084,146 | identical |
| JSPI | 11.041 | 10.898, 11.029, 11.041, 11.041, 11.050, 11.281, 11.680 | 4,084,146 | identical |

The oracle reported 300/300 frames, zero interpreted instructions, equal trace hashes (4e568988, trace
304ac2d89f83eebdaae83c7a1b129d417656732357eb1a30e1713a6cf7cabc75 in the retained run), and checksum
88bf80fb. These are engineering fixture measurements, not game-frame or 60fps claims.

### Static emitted-code attribution

On the shaped workload's emitted C, before the experiment: 768,650 bytes; 7,742 CPU-state register references
(2,765 loads, 4,896 stores plus address uses), 229 state-load synchronization sites, 426 state-store
sites, 1,014 boundary edges, 421 span-pointer calls plus 224 operand checked-pointer calls, 110
live-mask ALU sites plus 364 full-flag ALU helper sites. These are static operation counts, not line counts
or dynamic costs. The earlier shell line-count observations (736/229/426) were corrected by regex operation counts.

The actual emitted wasm was inspected with Binaryen wasm-dis. In the hot named function
R_01001180_01001180, there were 15 initial GPR state loads plus flags/clock/budget, 28 wasm locals, and
8,326 WAT lines. The full x64-crt baseline also showed 35,709 state-register references in emitted C, 2,495
memory operations, 2,508 guard-pointer calls and 1,304 ALU helper sites for 5,345 lifted instructions.

### Dynamic attribution

A 100 us V8 named profile of the shaped workload's pre-change window retained 7,608 wasm samples:

| Symbol/class | Samples | Share |
|---|---:|---:|
| xl_alu_full | 1,673 | 22.0% |
| lifted R_* regions (combined) | about 2,200 | about 29% |
| xl_pointer_checked | 640 | 8.4% |
| x64_shift | 606 | 8.0% |
| x86_host_alloc plus x86_map | 942 | 12.4% |
| x86_sched_next plus wake_waiters | 483 | 6.35% |
| other wasm | remainder |

This profile includes 100 fresh instances, setup and startup. Its allocation share is **not per-update
allocation**: parent-stack audit puts 438 host-allocation samples under w32_gdi_init/w32_boot, 295 under
w32_boot, 42 under decode_at/x86_lift_block (decode-cache setup), 10 under code-range registration, and one
nested allocation under GDI init. All 156 x86_map samples are under w32_boot/bgt_init. Thus at least
889/942 allocation+map samples are directly setup-owned, not an import-path allocation loop.
The scheduler row comprises x86_sched_next 205 and wake_waiters 278: stacks lead from w32_update and
w32_thread_schedule. Each fresh run performs startup then 300 Sleep-driven updates; scheduler share is
partly the intentionally idle tail. These startup-inclusive shares rank helpers but do not establish
a sustained VM-only time split or a game-like scheduler bottleneck. A one-instance warmed profile was
also tried and ran successfully, but it samples only the idle tail and is not retained as the hot profile.
Next session needs a repeated-work window or preprepared instances to separate useful-work attribution.

## Rejected experiment

A scratch-only emitter variant made all boundary register stores conditional on the dirty mask, including
interior/fault boundaries. It preserved checksum, lifted/interpreted trace identity and zero interpreted
instructions. It did not establish a speedup: sequential fresh-instance medians were 11.878 ms Asyncify and
11.090 ms JSPI versus corresponding baseline 11.679 and 11.041 ms (noise/slight regression). It also
requires careful fault-boundary auditing, so it is not retained. The working emitter is restored unchanged.
