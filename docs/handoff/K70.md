## 1. Q126: transport bursts busy-poll WebGPU request results

**Cause (reproduced).** The guest's `wait_request` (`w32_gl.c:608`), and the readback waits in `w32_gl_*.h`, poll
`bgt_request_status` and yield (`w32_wait_transport`, a time-neutral transport yield). On WebGL2 a shader/readback
result completes synchronously inside the update's render, so the next update sees it. On WebGPU it completes
asynchronously (`getCompilationInfo`, `mapAsync`) outside `host.ioWork`: K66's burst rendered and re-ran the update at
once, the guest polled 0 again, ~1000 times per tick. Each of those renders did `getCurrentTexture` + present blit +
`queue.submit`, so the GPU process queue filled and the shader result itself arrived late. Fixture before the fix:
**32.3k updates/s, 1087 updates/tick, 190 ms per program** on the page vs 15-38 ms per program back-to-back, i.e. the
r29 numbers (32.7k/s, ~200 ms/program). The latency is therefore a kit cost, not inherent async compilation.

**Fix (`bgt/runtime/requests.ts`, `host.ts`, `runtime.ts`, `page-pacing.ts`).** No ABI change.
- `Requests` remembers the request the current update last polled with status 0 (`polled`, cleared by `advance()`);
  `awaited()` returns it only if its result has **not arrived** (a result that arrived but is visible only at the next
  update boundary returns null: the next update makes progress, e.g. resident file reads). `whenDone(token)` settles on
  completion or close (cancel). Never guest-visible.
- `GameHost.transportWait()` = `whenDone(awaited())` or null.
- `transportBurst`: after rendering the update and settling host I/O, if `transportWait()` is pending, wait for it
  with `settlesWithin(wait, remaining tick budget)`; on timeout the tick ends (its last render is the tick's present)
  and the next tick continues. Counters in `pageLoop()`: `requestWaits`, `requestWaitMs`, `requestWaitTimeouts`.
- `?iowait=0` (runtime option `ioWait: false`) restores the pre-K70 re-run (A/B; `BGT_K70_IOWAIT=0` in the spec).
- Kept K66's gain: file reads resolve in `ioWork` (settled before the check) or synchronously (resident), so
  `requestWaits` stays 0 on `file-load` (670-719 ms on all four runs, K66 674-827 ms).

**Measurements** (`tests/e2e/gl-programs.spec.ts`, console `K70 gl-programs`, 24 programs = 48 compiles + 48 link
stage modules + 24 glReadPixels = 120 blocking results; before = `BGT_K70_IOWAIT=0`):

|---|---:|---:|---:|---:|---:|---:|
| before, WebGPU JSPI | 4,564 | 911 | 195 / 147,543 | 32,285 | 1,087 | - |
| before, WebGPU Asyncify | 3,481 | 397 | 158 / 119,926 | 34,406 | 1,061 | - |
| before, WebGL2 Asyncify | 255 | 257 | 14 / 121 | 420 | 10 | - |

## Review vK70 follow-up

Independent review vK70: PASS (no correctness bugs); lows fixed:
1. **Wait cause.** `GameHost.transportWait()` waits for whichever comes first, the polled result or pending host I/O
   (`Promise.race` with `settleRequests()`), and `Requests.reserve()` drops the poll: a request issued after the
   poll is the newer cause of the yield. Unit (`requests.test.ts`): a never-resolving GPU result polled without
   blocking every 10th update of a 200-read resident ReadFile loop causes 0 waits (each would cost a tick budget:
   ~1 read/tick); a streamed read ends the wait when its I/O settles.
2. **Waiter leak.** One shared promise per pending request (`whenDone` deduplicated; 100 waits = 1 waiter);
   `restoreRequests` releases all waiters (`wakeAll`).
3. **ABI wording** (§2): guest-visible results identical; the number of time-neutral polling updates depends on wall time.
4. **JSPI publish check** now inspects the bytes (`assertJspiArtifact`: no `asyncify_*` export, no Asyncify marker);
   unit: the optimized artifact passes, an Asyncify-transformed one is refused.
5. **Cache keys hash the exact flags** (`asyncifyArgs()` / `jspiOptArgs()` are the arguments actually run and the key
   input, removelist path replaced by `<removelist>`; its contents stay keyed by `asyncifyRemove`). This invalidates
   every Asyncify/JSPI cache entry once more; artifacts are byte-identical (x64-gl-programs rebuilt: same sha256 for
   both). `asyncify-cache-key.test.ts` covers flag changes for both.
6. **Device loss during a wait** (`gl-programs.spec.ts` second test, both backends x modes): loss 60 ms into the
   startup, the wait settles (the lost renderer completes pending results with E_IO), startup finishes, the loop keeps
   ticking, `pageLoop().maxTickMs` (new) < 250 ms, page not failed.

Gates after the fixes: typecheck, `npm run lint` (eslint, gcc-14, clang `--check` of all examples, cold after the
key change), leakcheck ok (1203 files); units requests, page-pacing, jspi-opt, asyncify-cache-key,
