**Deliberate compatibility choice:** VAO0 has implicit element-buffer storage even in the advertised
core context. Binding/unbinding it and Data/SubData/map/flush/unmap uploads work; buffer data belongs
to the buffer object, not the VAO, and survives unbinds and later named-VAO references. The other eight
GL3.3 buffer targets are context state and were already legal without a VAO; they need no leniency.

**Attribute setup and draws with VAO0 remain GL_INVALID_OPERATION**, including Pointer/IPointer,
Enable/Disable and Divisor. Reviewer bridge decision **#137** explicitly accepts this conservative
boundary until a porter supplies evidence requiring more. Do not infer from element-buffer leniency
that every vendor also accepts all attribute/draw operations. There is no new physical Windows-driver
experiment here. Normative contrast: OpenGL 3.3 core §2.10 / appendix E removes the ordinary default VAO;
this lane intentionally follows the supplied Windows observation for element storage only.

References consulted: [OpenGL 3.3 core specification](https://registry.khronos.org/OpenGL/specs/gl/glspec33.core.pdf),
§2.9.2–2.9.3 / tables 2.10–2.11 for store/mapping state and flags;
[MapBufferRange](https://docs.gl/gl3/glMapBufferRange),
[BufferData](https://docs.gl/gl3/glBufferData). These document the ordinary GL contract, **not** an
independent vendor certification of the reviewer-provided compatibility evidence.

## Implementation

- `w32_gl.c` uses the existing reserved `vaos[0].element` slot without turning name zero into
  a generated public VAO. Gen/Is/DeleteVertexArrays and strict attribute/draw checks are unchanged.
  The deletion loop also clears default-element references.
- Every accepted VAO0 element bind, Data/SubData upload, map, and mapped upload calls the existing
  `approximate` machinery: increments `gl_approximations` on **each call**, deduplicates
  `gl_approximation_kinds`, logs `GL approximation or unsupported: <kind>` once per kind.
  Kinds: `core VAO 0 element-buffer binding`, `data upload`, `sub-data upload`,
  `map`, `mapped upload` (the latter four share the same prefix).
  Rejected operations do not receive leniency credit. Binding/querying a real VAO is not counted.
- `w32_gl_buffer.h` replaces explicit unsupported MapBuffer/MapBufferRange/FlushMappedBufferRange/
  UnmapBuffer/GetBufferPointerv with real bounded guest-heap staging. Checks flags, signed/full-width
  offsets/lengths and mapping state. Map pointers are guest addresses, never native/host addresses;
  freed on unmap, accepted deletion and store replacement. BufferData implicitly resets mapping state
  as required by table 2.10; unmap retains BUFFER_ACCESS and resets other mapping state per §2.9.3.
- Non-invalidated maps snapshot the actual data. GPU-generated bytes use ordered BUFFER_READBACK,
  never the stale CPU upload shadow. Invalidation permits discarding prior bytes; unsynchronized is
  accepted without promising an asynchronous implementation. Flush offsets are relative to the map,
  and only explicitly flushed bytes commit; later unflushed guest writes do not leak into the store.
- Odd-byte partial writes to generated storage snapshot native neighbours and upload an authoritative
  full-store replacement, avoiding the wire backend's generated/unaligned partial-update restriction.
  Aligned partial uploads retain generated authority. Submission/readback/OOM failures return actual
  GL errors, clean scratch/staging, and do not claim an accepted upload or modify the CPU shadow.
- Mapped stores cannot be copied, subuploaded, read via GetBufferSubData, or consumed as enabled vertex,
  index, uniform-block or active transform-feedback buffers by draws. Buffer parameter/pointer queries
  expose the real mapping state. GPU mutation paths preserve pending padded-UBO cleanup ordering.

## Stricter-than-Windows / dropped-work audit and recommendations

Rejected cases below signal GL errors; inaccurate queries and lifetime mismatches are called out
separately. Applications that do not inspect glGetError can nevertheless appear to lose work. Only the evidenced Q57 path and the mapping
contract required by this brief are changed here.

| Path | Finding / disposition |
|---|---|
| Element binding with VAO0 | **Fixed**, supplied Windows evidence; storage/data preserved and every leniency counted. |
| Other eight buffer targets with VAO0 | Already accepted as context state; native regression binds/uploads each of all nine targets. No broadened error suppression. |
| BufferData on an unbound target | **Keep GL_INVALID_OPERATION**. There is no default buffer object zero and no supplied Windows evidence for inventing one. Regression asserts error and existing object data survives on all nine targets. |
| VertexAttribPointer without VAO / without ARRAY_BUFFER | **Keep explicit core errors**; reviewer approved VAO0 boundary. Client-memory attribute emulation is not justified by Q57. A future expansion needs vendor/target evidence and owned guest snapshots, not pointer reinterpretation. |
| BufferData with size zero | Existing `size <= 0` rejects a valid zero-sized store. Recommend representing an empty GL store without a zero-sized native allocation, plus replacement/recovery tests. Not present in supplied Q57 sequence; not repaired here. The 64 MiB positive-size bound remains explicit. |
| BufferData usage / GetBufferParameteriv BUFFER_USAGE | Existing upload ignores the hint and query always returns STATIC_DRAW, even after DYNAMIC_DRAW. Recommend validate/store/report all nine legal hints. No need to change native allocation strategy. Not a measured Q57 cause. |
| DeleteBuffers references in noncurrent VAOs | Existing code deletes native storage and clears references in **all** VAOs; desktop deferred deletion can retain referenced storage in unbound VAOs. Recommend separately tested reference/object lifetime handling, not a VAO0 special case. No captured delete/reuse failure supplied here. |
| IsBuffer after bind before storage | Existing query tests `gpu != 0` rather than realized object existence; can mislead callers into skipping uploads. Recommend distinguish reserved generated names from realized-on-bind objects; no such branch evidenced in Q57. |
| Generated index data / generated odd SubData, restricted attribute formats | Existing explicit BAD_OP/BAD_ENUM boundaries remain. Map uploads now handle generated odd writes correctly; this does not certify GPU-generated indexed-fetch bounds or add missing vertex conversions. Use focused native-pixel regressions before expanding these separate paths. |
