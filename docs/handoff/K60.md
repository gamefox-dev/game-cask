## What changed

**Q115(b): GL errors no longer flush (`w32_gl.c` `fail`, `w32_gl_query.h`).** While deferred calls are pending, a
profile validation error is latched at once (callers still use it for control flow) and its stream position
(`err_seq` = newest deferred sequence number) remembered. When the batch settles and a deferred call at or before
that position failed (whole-list replay or `bgt_submit_failures` offsets), that call's error preceded the latched
one: glGetError returns it (`latch_fix`). First-error order is therefore exact without a flush. Regions that save and
restore `error` themselves (`cleanup_send`, `reclaim_slack`, `buffer_store`'s CREATE) keep the K53 flush
(`latch_local`); the API wrapper publishes the outer latch (`latch_outer`).

**Q115(b) root cause too: GL 3.3 capabilities.** glEnable/glDisable/glIsEnabled/glGet of every GL 3.3 core capability
are tracked state, not GL_INVALID_ENUM (real GL accepts them). DITHER and MULTISAMPLE (initially enabled) never change
rendering; enabling another unrendered capability (logic op, depth clamp, framebuffer sRGB, line/polygon smooth,
polygon offset, primitive restart, program point size, sample coverage/mask/alpha, seamless cube maps, clip
distances) is a counted approximation; rendering is what the base rendered after rejecting the call.

**Q115(a): current attributes.** Each program's private uniform buffer (usage uniform|vertex) gets a 256-byte tail;
a single-instance draw that reads generic current attributes writes them there, in the same batched BUFFER_UPDATE as
its uniform values, and binds its constant vertex slot to it. The draw thus depends on one upload (its IF_HEAD chain
is unchanged and exact), and the synchronous upload to the private buffer 1023 (2 ABI submits per such draw) is gone.
Instanced draws with constants keep 1023 (synchronous, as before).

**Q115(c): renames.** Profile: the program uniform buffer is a ring of 256-aligned slots (values + tail, at most 16
slots and 32 KiB per program); each draw uploads to and binds the next slot. WebGPU (`gpu.ts`): the pending frame
encoder's buffer use is tracked per byte range (vertex/index/uniform bindings, capture gathers and scatters); a
BUFFER_UPDATE whose 4-aligned range no earlier command uses writes the native buffer directly; overlapping writes
rename or split as before. Remaining renames are in-place stream re-specifications at offset 0 that the previous
batch still reads (22 in the fixture: 8 batches x 3 buffers, minus first uses).
WebGL2 (`webgl2/gpu.ts`): a partial update of a CPU-authoritative store of <= 32 KiB re-specifies the whole store from
the exact shadow (`bufferData`), because ANGLE Metal orphans a fully replaced store but synchronizes/copies around
in-flight reads on a partial `bufferSubData`. Without this the ring made `x64-gl-respec` 0.4 ms/frame slower on WebGL2
(bisected: exact-size uniform buffer 1.37 ms, ring 1.80 ms, ring + re-specify 1.33 ms). `?gpubatch=0` keeps sub-data.

**Q117: capture cache (`gpu.ts` `captureProgram`).** The translated vertex stage (translateGLSL + depth lowering +
bindings) is cached on the pipeline resource per sampler specialization (depth slots, sampler words), and the lowered
compute pipeline per draw shape (inputs, topology, counts, first/base, index layout). Invalidated with the pipeline
(PIPELINE_DELETE, re-create on relink, device restore), on FEEDBACK_VARYINGS, and when the shader handle names a
different shader object. A steady capture draw creates no shader module, bind-group layout or pipeline. Counters
`lastFrame.captureTranslations` / `captureLowerings` (misses) and `renameBytes`.

## Q116 (WebKit 5 fps page loop): not reproduced; one candidate mechanism removed

Not reproduced on any CC0 fixture (`x64-gl-respec`, `x64-gl-batch`, `x64-gl-current`, `x64-gl-frame`; base and final;
JSPI and Asyncify; `?gputiming=1` on and off; merged and `?gpubatch=0`): WebKit WebGPU page loops run at 57-60 fps.
Synthetic WebKit probes (`wk-synth.mjs`, plain WebGPU) did not stall either with: 4 MiB/frame of copy-on-write
renames from a recycled pool, writes into buffers the open encoder uses, 22 ms of synchronous or setTimeout-chunked
main-thread work per frame, timestamp queries with per-frame mapAsync, mappedAtCreation scratch buffers destroyed
after submit, or invalid command buffers.

Found: in WebKit, `createShaderModule` of a large module costs ~6-7 ms of GPU-process time while the web process spends
< 0.1 ms; from about 3-4 such modules per frame the rAF rate falls although the main thread is idle (4 x 2000-line
modules: 40 fps; 10: 14.7 fps; Chromium 50 fps with 2.5 ms main-thread cost). That is the observed Q116 shape (main
thread mostly idle, rAF throttled). The base WebGPU renderer created a new shader module for every transform-feedback
capture draw, even on a pipeline cache hit; after Q117 a steady frame creates none. Whether this was the game's 200 ms
cause is unverified (it does not explain why `?gpubatch=0` was faster). Porter check: WebKit WebGPU page fps with
`lastFrame.captureTranslations` (expected 0 in steady frames).

## Findings for the porter / coordinator

1. r27's `flush_pending < api_Clear` and `flush_pending < draw` stacks are `fail()` inlined: the game raises profile
   errors in glClear (scissored or masked clears are rejected with GL_INVALID_OPERATION, `w32_gl_draw.h` api_Clear;
   real GL clears the scissor box) and in draws (e.g. GL_TRIANGLE_FAN, which `topology()` rejects with
   GL_INVALID_ENUM). They no longer cost a flush, but the game may be missing those clears/draws: a guest-visible
   correctness gap (not changed here; needs its own lane).
2. In-place stream re-specification at offset 0 still renames on WebGPU when the previous batch reads the buffer;
   avoiding it needs the profile to place orphaned stores at new offsets (deeper change).
