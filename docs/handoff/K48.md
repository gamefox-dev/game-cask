## Diagnosis and fix

Confirmed the coordinator's diagnosis locally: default Asyncify artifacts have no JSPI variant; runtime intentionally falls back. The four reported cases (in two spec files) failed at the exact existing suspension assertions with Expected `jspi` / Received `asyncify`. Local host is macOS, not a Linux runner; reproduced CI's artifact policy and software-renderer Chromium project, not a full GitHub run.

- Shared `openGame` now preflights an explicit JSPI request (also suite-wide `BGT_E2E_SUSPENSION=jspi`) against **browser APIs and the browser-routed manifest** before boot. A JSON-document navigation runs browser init scripts without booting the runtime; unlike APIRequestContext/disk reads it honors synthetic fixture routes. Both prerequisites must exist. Optional cases skip with a reason naming every missing capability. `BGT_TEST_JSPI=1` makes either absence a hard failure. Admitted cases must actually report JSPI after boot.
- This centrally covers savestates, transfer, services, failures, compaction and recording variants. JSPI-only synthetic manifests count as real JSPI artifacts, independent of the built example's variants.
- Recording comparison no longer silently compares Asyncify against itself. Existing loader fallback/error tests explicitly opt out of the strict mode gate, retain fallback assertions, and account for browser support as well as variant availability. The direct GameHost regression uses the same optional/required browser policy; it compiles its own raw artifact.
- Runtime fallback policy is unchanged. New `diagnostics.suspensionSelection` exposes effective `requested`, `supported` and `variantPresent`, including failed selection; active mode remains `diagnostics.suspension`. Units cover all four capability combinations, dual/JSPI-only manifests and explicit/preferred requests.
- CI workflow/build cost is unchanged; no switch to dual in tier 2.
