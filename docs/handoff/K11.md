## Configuration and implementation

```json
"pipeline": {
  "platform": "win32",
  "liftPreset": "fast",
  "liftInlineMemory": true,
  "liftInlineAlu": true,
  "liftAffineCounting": true,
  "liftOptimizeSmall": true
}
```

Omitting all options is `size` (four false values); `fast` enables all four, and explicit booleans override the
preset. Both presets run the same guest contracts. Options are validated before pipeline work, forwarded to
both monolithic and chunked lifting, hashed into codegen cache keys and recorded as `manifest.pipeline.liftPolicy`.
The equivalent x86tool CLI uses `--lift-preset fast|size` and `--lift-inline-memory on|off`,
`--lift-inline-alu on|off`, `--lift-affine-counting on|off`, `--lift-optimize-small on|off`.
The policies specialize AMD64; i386 emission remains unchanged and participates in oracle checks.

- Memory: one inline same-page/in-range/mapped/unprotected operand check, full bounds/protection/cross-page
  validation out of line. Full-width addresses are never truncated before validation. Pointers never survive
  a call, memory growth, generic boundary or suspension. Whole-span guards retain the monotonic protection gate.
- Flags: specialized op/width/live-mask ALU emission, no generic full-ALU call on the fast policy. Immediate
  ADD/SUB and CMP/TEST plus INC/DEC can reconstruct missing flags on the cold fault edge from surviving register
  state. No hot-path operand journal and no repeated loads/stores. Alias writes, implicit stack mutations,
  destroyed dependencies and unrecoverable operations retain conservative precision. RMW/INC fault ordering
  retains the reference's exact flags, including its partial store behavior.
- Attributes: only regions of <=4 instructions lose `minsize,noinline` under `liftOptimizeSmall`. A <=64
  experiment grew code and did not show a robust speed payoff, so it was rejected. No coverage hot-list claim.
- Counting: affine debt uses static instruction positions; forward skips adjust debt, sequential blocks do not
  update clock/budget. Backedges, calls, exits, generic instructions/RDTSC and faults settle exact counts.
  A region-sized reservation bounds execution before the next check; near a quantum edge, cold semantic dispatch
  preserves the precise unexecuted instruction, yield and TSC behavior. Interior entries remain legal.

### Memory-fault / SEH scope (reviewer correction)

The original brief assumed Windows memory-fault exception records/resumption. Current runtime memory faults
**abort**, via `x86_fault`/`bgt_abort`; they do not enter SEH. Reviewer explicitly corrected that acceptance boundary.
This lane preserves exact fault CPU bytes, addresses, diagnostics, memory and cross-page partial stores anyway;
no exact-fault assertion was weakened. Explicit RaiseException/unwind/landing-pad behavior remains covered by
x64-cpp/tls and their identical oracles. Future memory-fault SEH delivery must extend cold reconstruction to every
live architectural dependency (or deopt before the first irreversible operation) and add exception dispatch; do
not mistake the present recoverable recipes for universal SEH-ready deoptimization.

## Measurements

Full samples, resource snapshots, build/cache data, oracle hashes and exact dispatch throughput are committed in
[`K11-measurements.json`](K11-measurements.json); compact policy comparison is
[`K11-benchmarks.json`](K11-benchmarks.json). `docs/pipeline.md` records per-step cumulative wasm/time values.
Measurements were sequential on the same macOS arm64 machine/Node 24.19.0/Zig 0.13.0; shared-machine load is
recorded, **not** claimed idle. Whole wasm includes profile/Asyncify. Startup timings include 300 host frames,
not pure guest CPU time. Throughput divides the identical reference-oracle guest-dispatch count by elapsed time,
not static instruction memberships or REP iterations.

Final policy comparison (five batches after warmup, 24 fresh instances/batch; ms per 300-frame instance):

| Fixture | size wasm B / ms | fast wasm B / ms |
|---|---:|---:|
| x64-crt | 1,259,242 / 2.668 | 1,330,663 / 2.803 |
| x64-cpp | 2,670,595 / 3.344 | 3,285,339 / 3.366 |
| codegen-cpu, 32 rounds | 1,378,250 / 5.369 | 1,390,993 / 7.835 |
| codegen-cpu, 1024 rounds | 1,378,251 / 95.347 | 1,390,995 / 95.659 |

The longer workload executes **36,709,146 dispatches**, ~385M/s size versus ~384M/s fast. Earlier cumulative
long-workload measurements were 97.997→95.988→91.670→93.148→95.594 ms for baseline/memory/flags/attributes/counting.
Keep every sample; do not cherry-pick the favorable run. Existing F-PERF-CRT's older 2x acceptance remains unmet.

Residual flag materialization: x64-crt 84.33%→83.56%, x64-cpp 71.77%→70.25%, CPU 1.60% unchanged (static ALU
sites; cold replay excluded). A rejected no-fault-barrier experiment measured cpp 3.365 ms/crt 2.785 ms versus
exact-policy repeat 3.317/2.654 ms; it did not establish a >5% barrier cost, so exact state was retained. Reviewer
allowed non-reconstructed abort-only flags if such a cost were proven; that relaxation was **not used**.

Reviewer interpretation: the synthetic fixture is ~386M dispatches/s, whereas porter run 6 observed ~3.4M
**lifted calls**/s. These are different counters/workloads, not a rigorous per-call equivalence, but the ~100x
scale difference is a strong reason to investigate game-build-specific call/API/Asyncify behavior with K10
instrumentation, not declare the engine bottleneck solved by synthetic per-instruction optimizations.

Reproduce:

```sh
BGT_CODEGEN_PRESET=size BGT_CODEGEN_IDS=codegen-cpu,x64-cpp,x64-crt BGT_CODEGEN_TRIALS=24 \
  BGT_CODEGEN_REPORT=/absolute/size.json npx vitest run --config tools/bench/codegen.config.ts
# repeat with PRESET=fast; use ROUNDS=1024, IDS=codegen-cpu, TRIALS=3 for long CPU work
BGT_LIFT_POLICY_REPORT=/absolute/policies.json npx vitest run --config tools/bench/lift-policy.config.ts
```
