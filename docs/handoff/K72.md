## 1. Measurements

### Tools (new)

- `npm run bench:wasm-size -- --wasm FILE [--work node_modules/.cache/bgt/pipeline/ID] [--coverage FILE]`
  (`tools/report/wasm-size.mjs`): section split (code / data / name subsections / other custom), defined functions by
  kind (`N_` fast, `R_` exact regions, `F_` wrappers, x86 runtime, Win32 profile, SDK, other) with p50/p90/p99/max and
  the largest functions; `--work` re-lifts the build's chunks with `--fast-mark on` and fits bytes against emitted
  instruction classes (NNLS; collinear, use wasm-lines instead); `--coverage` splits lifted bytes into entered vs never
  entered. Reads `<artifact>.names.json` for stripped artifacts.
- `npm run bench:wasm-lines -- --wasm FILE --work DIR` (`tools/report/wasm-lines.mjs`): exact attribution of every
  lifted code byte to a line of the generated C (line table, plus the call line of the outermost
  `DW_TAG_inlined_subroutine` for inlined helpers), and of each line to a guest instruction class via the marked
  re-lift. Build once with `"cflags": ["-gline-tables-only"]`, `BGT_KEEP_DWARF=1 BGT_JSPI_WASM_OPT=0` (new measurement
  env in `build.mjs`: keep DWARF). Sizes are pre-wasm-opt (use the shares). Needs llvm-dwarfdump.
- `x86tool lift --fast-mark on`: comments only (function marker on the existing comment line, `/*@op*/` before each
  instruction, `+` for inlined copies); unit-tested to be the unmarked text once comments are removed.
- `npm run bench:k72` (`tools/bench/k72.test.ts`): `BGT_K72_STEP=prepare|time|coverage`, fixtures `k65`, `cpprt`,
  `calls`, `vm`, variants `base sync out compact inl16 compact16 base0 compact0 oz`. Prepare builds dual and checks
  every variant's guest lines and per-update state hashes equal the base variant's in both suspension modes (cpprt:
  also equal to the native build of the same source). Coverage writes a recording and the never-entered split.

## 2. Candidates

### (a) Emitter density: done, opt-in

- **`liftFast.sync: "minimal"`** (`--fast-sync minimal`, `tools/x86/lift64_fast.h` `l64f_flow`): per function (and per
  inlined copy, with the caller's state as entry) a forward dataflow of registers written since the last point where
  `X` and the locals agreed (entry reload, a returned call, a generic instruction), and a backward GPR liveness in
  which spills are reads. Call sites, returns, exits and poll exits store only dirty registers; after a call only live
  volatile registers and RSP reload. Inlining decisions are computed by the same traversal as emission (`l64f_decide`,
  asserted equal at emission). Same Win64 assumptions as the full form; none added. Faster: 22% on the call-dense K52
  fixture (fewer stores), neutral elsewhere.
- **`liftFast.calls: "outlined"`** (`--fast-calls outlined`): `xf_enter(pc, flags, clock, qbase)` (publishes the clock
  and flags, `X.eip`, takes a depth slot), the plain C call, `xf_leave(next)` (releases it, abnormal-exit check),
  `xf_check(next)` after generic instructions; `x86_rt.c`, declared in `x86_guest.h`. Identical semantics to the inline
  form. Costs two small calls per guest call: +5% on dense small calls, +15% when every call is real (inline 0).
- **`liftFast.inline: "16"`**: existing knob; -15% size. Slower on k65 and vm (+6%), 3x faster on the calls fixture
  (inline 48 made its kernel too big). Speed effect is workload-dependent: measure on the game.
- Not done (ranked by measured share): shared cold exit blocks (exits/polls, ~5%); trimming the entry prologue reload
  per entry (6%); XMM registers in locals (SIMD 98 B each, also a speed item); per-call depth slot in the callee.

### (b) -Os/-Oz for cold functions: dropped

Whole-module `-Oz` changes lifted code by under 1% (cpprt 6.22 -> 6.16 MB, k65 identical): the lifted C is straight
line code over `always_inline` helpers, already what `-Oz` produces. The whole -4.0% / -7.7% is the runtime (0.86 ->
0.61 MB, constant). Speed neutral (k65 0.804 -> 0.803 ms). Not worth a hot/cold TU split.

### (c) Lazy code loading: designed, not built

What it would buy is what (d) buys in memory (an engine only compiles shipped code; WebKit compiles a module at load),
with native instead of interpreted speed when off-recording code runs. Design that works under both suspension modes
without wasm-split or synchronous compilation: lifted calls to cold functions already go through a weak symbol
(`N_x && ...` else return to the driver), and the driver interprets the target. Make cold functions a second module
(PIC side module importing memory, table and the runtime's symbols), fetched and compiled in the background on the first
miss while the interpreter runs the function; on instantiation the registry (`x86_register_lifted`) and the weak slots
become table entries and later calls go native. No guest frame ever waits on the fetch, so neither JSPI nor Asyncify
needs to suspend inside lifted code. Cost: dylink loader in the runtime, a PIC build of cold chunks (GOT access in cold
code only), per-module granularity (one cold call compiles that whole module: cluster by call graph). Gate: only worth it
after (d) shows how much interpretation a recorded selection costs on MMX8.

### (d) Ship only reached functions: done, opt-in

`pipeline.selection: "recorded"` (`tools/build/coverage.mjs`): selected = owners of recorded entries, no static
closure. Unrecorded code interprets and is recorded (inbox), so builds converge (cpprt: 2 builds). Not for strict
slices (they keep their own closure). Builds record `selection.mode: "recorded"`.

### (e) Name section: done, opt-in

`pipeline.wasmNames: "strip"` or `BGT_WASM_NAMES=strip` (`build.mjs` `wasmNamesMode`, `wasm-names.mjs`
`stripNames`): after both artifacts are final, removes the `name` section and writes `<artifact>.names.json`
(`game-cask/wasm-functions/1`, index -> name, artifact sha256) beside each; manifest sizes/hashes are of the
stripped bytes; `pipeline.metrics.wasm_names` and `wasm_names_stripped_bytes`. Default `keep`.

## 3. Projection for the 244 MB MMX8 JSPI module

Code is >99% lifted. The fixtures bracket the effect: k65/x64-scale are ALU-dense synthetic code (few calls), cpprt is
compiled C++ library code (call-dense, like an engine). MMX8 emits 97 B per lifted instruction against cpprt's 73,
which points to at least cpprt's call density (more inlined copies, larger functions). Bracket: compact16 -8%..-34%
= **145-224 MB** (likely nearer the cpprt end); WebKit at the K71 marginal 4-5 MB/MB (flattening above 30 MB) and
the cpprt-measured 6 MB/MB: **-80 .. -500 MB of WebContent**; Chromium scales with executed code only (2-4 MB/MB).
`selection: "recorded"` then removes the static closure's share (cpprt: half of the selected lifted bytes). The
porter can read both before building: `pipeline.json` `selection.recorded_owners` vs `static_closure_owners`, and
`npm run bench:wasm-size -- --wasm .../game.jspi.wasm --coverage <recording>` for never-entered bytes.
