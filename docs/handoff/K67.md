# K67 — WebKit WebGPU canvas pacing (Q116) and instanced current attributes (Q115)

Branch `kit/lane/K67`, base `f5f988d` (v0.3.0-dev.37). CC0 fixtures only; no game files, installs or pushes.
Network (read-only, needed for Q116): WebKit sources from GitHub (`raw`/contents API) and Sourcegraph search.
Evidence: `/Volumes/CaskWork/lanes/scratch-K67/` (`wk/` synthetic WebKit WebGPU probe + runner, `wksrc/` the WebKit
files read, build/test logs, `perf/` measurement JSONL); harness `K67/reports/k67-perf/kfps.mjs` (git-ignored).

## Q116: root cause — WebKit's WebGPU canvas frame pacer

WebKit (`Source/WebCore/platform/graphics/WebGPUFramePacer.cpp`, fed by `GPUCanvasContextCocoa::updateFramePacing`)
sets the page's preferred rendering-update rate for a WebGPU canvas from two values per presented frame:

- `lastFrameGPUCost`: the largest `GPUEndTime - GPUStartTime` of the command buffers that used the canvas texture
  (`CommandBuffer.mm` completion handler -> `recordGPUExecutionWindowOnCanvasTextures`), and
- `lastFramePresentStall`: how long `present()` blocked waiting for an in-flight frame slot.

After 4 consecutive presents that stalled >= 1 ms it steps the rate down the display's divisor ladder to the first
rate whose interval covers the median stalled frame cost; it steps up only when stall-free frames have a median
cost that fits a faster rate. The ladder is the divisors of the nominal display rate. Headless Playwright WebKit on
the M4 runs at 85 Hz (r27 `plain` 84.9 rAF/s), whose ladder is 85, 17, 5, 1 Hz: any frame cost above ~11.8 ms gives
17 Hz, above ~60 ms 5 Hz, and once there a frame cost that stays above 11.8 ms never steps back up.

The kit's merged frame (K53) recorded *everything* — all §13 passes, compute captures, blits, then the presentation
draw and snapshot copy — into one command buffer, so the canvas texture's GPU window was the whole frame's GPU
window. `?gpubatch=0` submits each pass separately and records the presentation into its own short command buffer,
so WebKit saw a tiny cost and never stepped down: exactly the r28 split (merged 5.0 fps, `gpubatch=0` 38.7 fps,
busy_ticks 0, rAF every 200 ms, while back-to-back stepping — which never presents through rAF pacing — is fast).

Bisect (synthetic plain-WebGPU probe in WebKit 2370 / 27.2, `scratch-K67/wk/synth.html`, rAF/s over 3 s):

|---|---:|---:|
| 65 renames x 21 KiB from a pool, 77 draws / 10 passes, one command buffer | 85 | 60 |
| same, renames created per frame + destroyed after submit | 85 | |
| same, + 22 ms main-thread work per frame / work split over 4 tasks / render outside rAF | 43.7 / 84.7 / 83.6 | |

So none of the brief's candidates (buffer creation/destruction, destroy timing, copy vs writeBuffer, mapping,
encoder size, getCurrentTexture timing) moves the rate; only the GPU window of the canvas-touching command buffer
does. Why the game's merged command buffer reported > 60 ms while its timestamp-query pass time is 1.5 ms is not
established (the window brackets GPU execution, including waits inside the command buffer and GPU time slices taken
by other processes; the r28 host ran two other lanes' GPU workloads). It no longer matters for pacing: the canvas
command buffer is now the short tail only.

## What changed

**Q116 (`bgt/renderers/webgpu/gpu.ts` `flush`, `webgpu.ts`):** a merged frame is still one `GPUQueue.submit`, now of
two command buffers: the frame encoder's §13 work, then a fresh encoder holding only the presentation draw and the
snapshot copy (the only commands that use the canvas texture). Same for the 2D-pass branch. Queue order, pixels and
the submit count are unchanged; WebKit's pacer now sees the tail's GPU window (~0.1 ms). New per-frame counters
`lastFrame.commandBuffers` (2 for a merged frame) and `lastFrame.buffersCreated` (every `GPUDevice.createBuffer`
while the frame is drawn, via a census wrapper like the K53 submit census).

**Q115 (`platforms/win32/w32_gl_draw.h`, ABI §13.3 additive):** the constant vertex slot of a draw that reads generic
current attributes has **stride 0** and binds the 256-byte tail of the program's uniform ring slot (K60) for any
instance count. Instanced draws therefore no longer `ensure_current_buffer` (synchronous BUFFER_UPDATE of private
buffer 1023 = 2 ABI submits per draw). Only programs whose uniform size is not 16-aligned keep the 1023 path.
- ABI §13.3: stride 0 (previously E_INVALID) = every vertex and instance fetches the element at the bound offset;
  its attributes must end within 2048 bytes; the bound range must hold the element (`commands-gpu.ts`).
- WebGPU: `arrayStride: 0` natively (repacked UNORM8X4 slots keep stride 0 and one element).
- WebGL2: GL reads stride 0 as "tightly packed", so a stride-0 slot gets `vertexAttribDivisor(loc, 0x7fffffff)`
  (an instanced attribute never advances per vertex; no instance count reaches the divisor) and skips the >255-byte
  CPU repack (the old stride-256 constant slot was repacked on the CPU every draw).

**Buffer census (`gpu.ts`):** rename targets and the transform-feedback capture temporaries (gather + output
storage buffers, previously created per capture draw and destroyed after the submit) share the recycle pool, now keyed
by usage and size. Steady capture frames create no GPUBuffer (`x64-gl-frame` 18 -> 2, `x64-gl-respec` 40 -> 4 per
frame; the remainder is one 32-byte blit uniform per framebuffer blit).

## Findings for the porter / coordinator

1. Q116 porter check (WebKit, WebGPU, JSPI): real-page fps after the back-to-back windows, with
   `lastFrame.commandBuffers` = 2 and `nativeSubmits` = 1. Expected: the `?gpubatch=0` rate or better.
2. Not explained: why WebKit reported a > 60 ms GPU window for the game's merged frame (pass timestamps 1.5 ms).
   Candidates: waits inside the command buffer (e.g. for the canvas IOSurface) or GPU time slices of other processes
   on a shared host. If the game still paces down with the separate presentation command buffer, that would point
   at the tail itself (present + snapshot copy) and is the next thing to measure.
3. WebKit's pacer also stepped down transiently in 2 of 19 fixture windows with the fix (17.2, 21.2): a GPU-bound
   frame can still make the short tail command buffer start early and report a long window. It recovers when
   presents stop stalling; a GPU-light game should not hit it.
4. Before K67 the merged path inherited WebKit's (coarse) pacing in genuinely GPU-bound frames; now, like
   `?gpubatch=0`, it is back-pressured only by WebKit's in-flight frame limit (more queued frames, more latency).
5. Remaining per-frame GPUBuffer creation: one 32-byte uniform per framebuffer blit (`blit.ts`).
6. Playwright traces change WebKit's frame pacing (screencast cadence): page-fps measurements in WebKit must run with
   tracing/screenshots off.
