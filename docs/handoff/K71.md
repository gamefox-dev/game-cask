## What changed

### Q128: lazy native texture storage (both executors)

- **WebGL2** (`bgt/renderers/webgl2/gpu.ts`): TEXTURE_CREATE_EX creates a texture *name* only; `materialize()` issues
  `texStorage2D/3D` with every reserved level (`allocatedMips`) and, for depth formats, the BGT initialization clear,
  on the first use that needs texels: upload, pass attachment, sampling bind (`OP.TEXTURE`), blit (source or
  destination), readback (color and depth), mip generation from a materialized base. ALLOCATE_MIPS on a storage-less
  texture only raises the reservation. Inside a pass (sampling bind) the depth initialization saves and restores the
  draw/read framebuffer bindings, scissor test and depth/stencil write masks (cached WebGL state, no GPU round trip);
  draw buffer 0's color mask comes back from the bound pipeline (as CLEAR_BUFFER already does).
- **WebGPU** (`bgt/renderers/webgpu/gpu.ts`): `TextureResource` is a class whose `native` getter creates the
  GPUTexture (all reserved levels) on first read; every use site already reads `native`, so upload, attachment,
  sampling, blit, readback and mip generation materialize. Depth (and constant) initialization is its own submission:
  it precedes every later use in queue order, and no earlier command can reference a texture that did not exist.
  Delete of a never-used texture creates nothing; the copy-on-write split check looks at `live` only.
- **GENERATE_MIPS from a storage-less base** (color): the base holds its creation value 0, so the levels stay
  unallocated (exactly what a zero chain reads back); the recovery bookkeeping (`generated` without data) is K64's.
- **Clear-only passes** (needed for the real case: the Win32 profile's whole-attachment `glClear` is PASS_BEGIN with
  clears + PASS_END). A pass whose attachments all lack storage stays *virtual*: any in-pass op realizes it (the
  original PASS_BEGIN runs natively, with the attachments materialized first); if PASS_END comes first, the clears
  become per-level constants (color clear words, depth, stencil) and nothing is allocated. `materialize()` then
  clears each level to its constant with the same native clear call the pass would have issued (bit-identical).
  LOAD keeps the current value. `lazyTextures.deferredPasses` counts them.
- **Accounting** (`bgt/runtime/memory.ts`): `gpu.native.textures.bytes` / `depthStencilBytes` are materialized levels;
  new `textures.lazy {count, bytes, depthStencilBytes}` is the reserved rest, so `bytes + lazy.bytes` equals the
  decoder's `gpu.reserved.textures` exactly (asserted e2e on 6 fixtures and the probe, both backends). The decoder's
  reservation, validation and guest-visible results are untouched (no ABI or profile change).
- **FBO completeness** is the profile's (`resolve_fbo`, from guest state) and never needs storage; the executor's own
  completeness check runs at the native pass, after materialization.
- **Recovery / savestates**: restore replays TEXTURE_CREATE_EX lazily, then the uploaded levels (which re-materialize);
  never-materialized levels restore exactly (creation values). Cleared constants are rendered contents and are lost on
  recovery, exactly like rendered contents before K71 (`targetsLost`). Savestate capture reads levels back
  (materializing on the replay renderer) and restores them as uploads, unchanged.
- **A/B**: `?lazytextures=0` / `RuntimeOptions.lazyTextures: false` / executor `{ lazyTextures: false }` restores
  allocation at creation.

### Q129: texture recovery shadows — decision (a), default unchanged

- Manifest `gpu.recoveryShadows: false` (game.json `"gpu"` is already copied to the manifest by build.mjs; no
  tools/build change), `?recoveryshadows=0|1`, `RuntimeOptions.recoveryShadows`; precedence option > URL > manifest >
  default **on** (today's behaviour). A malformed URL value is reported in `backendNotes` and ignored; a non-boolean
  manifest/option value fails init.
- Off: executors keep no texture upload shadow (`TEXTURE_UPDATE_EX` marks the texture `unshadowed`; generated-mip
  shadow chains are not computed). **Loss semantics:** a loss before any texture upload still recovers exactly; after
  an upload, `restore()` throws `texture recovery shadows are disabled (gpu.recoveryShadows: false): N uploaded
  texture(s) cannot be restored`, which the renderers report as unrecoverable and the runtime turns into its existing
  `device-lost` stop with an accessible error (WebGPU: through the WebGL2-fallback refusal for live GPU resources). No
  silent restore with blank textures. Reported in `diagnostics().memory.gpu.recoveryShadows {enabled, source}` and a
  backend note. Opt-in test checkpoints need the shadows and refuse while they are off.
- Not done: (b) guest re-upload on loss (lifted guests do not handle loss), (c) one shared decoder/executor buffer
  copy (needs the K64 ordering design; buffers are 12 MB on MMX8 vs 152 MB texture shadows), (d) shadow compression.
  Buffer shadows are unchanged (load-bearing on both backends).

### Q131 part 2: `npm run bench:footprint` (`tools/report/footprint.mjs`)

- Launches Chromium (real GPU args, as r29) or WebKit with `BGT_FOOTPRINT_TAG=<nonce>` and
  `__XPC_BGT_FOOTPRINT_TAG=<nonce>`: launchd passes `__XPC_`-prefixed variables to XPC services (prefix stripped), so
  WebKit's WebContent/GPU/Networking services carry the nonce too (verified on this host). Owned processes are those
  whose environment (`ps -E`) holds the nonce: exact, unlike r29's name match / pid window, so other lanes' browsers
  never count.
- At `ready` and after the run (`--frames N`, `--until LOG_TEXT`) it records `__BGT_TEST__.memory()` beside macOS
  `footprint --json` (phys_footprint) per owned process, classified (page renderer = largest renderer / WebContent,
  GPU process, network, browser), with top VM categories and `unattributedBytes` = page renderer + GPU process −
  estimate. `--sweep ID,...` fits footprint against module size; `--query` passes URL parameters (A/B);
  `--parse FILE` summarizes saved `footprint` text or JSON. Ports import `launchTagged()` + `footprintSnapshot()`.
  Named `bench:*` so the lane heavy-command gate applies.
