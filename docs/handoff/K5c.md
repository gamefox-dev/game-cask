# Lane K5c — truthful, bounded selective-build discovery (Q17)

## Delivery

Implementation: `bcbcab2` (`fix(coverage): record bounded entries and select their owning functions`);
trace-parity assertions: `ddf99c7`. Branch `lane/K5c`; no push. This handoff is added separately after verification.

- AMD64 interpretation records dynamic block/continuation entries, not every decoded instruction. i386 uses the
  same accounting definition. Lifted AMD64 region/indirect dispatch records the actual continuation address;
  i386 continuation wrappers also record their actual address, not a falsely repeated function start.
- Host recording deduplicates addresses, unions lifted/interpreted kind bits, and retains a finite
  **1,048,576-address** safety limit (16× the former 65,536). Dropped **events** remain explicit. Both selective
  and strict builds still reject every input with positive drops; no trace filtering/overflow-flag removal.
- Analysis exposes half-open function `addr..end` ranges and `.pdata` provenance (`unwindRange`). A sweep/heap
  builds disjoint ownership intervals: unwind ranges take precedence over speculative interior seeds; otherwise
  the nearest enclosing analyzed start owns the address. Selection and static call closure normalize interior
  entries to that owner. Gaps never silently belong to the preceding function.
- All pipeline builds, including interpreter-only builds, register the same compact ownership metadata. Runtime
  census uses one byte per analyzed owner; it does not store executed instruction addresses. Range lookup caches
  both owned intervals and gaps. Transitions into gaps record before execution, preserving strict outside-slice
  stops without turning straight-line unowned code into instruction-by-instruction recording.
- `interp_insns` counts interpreted instruction dispatches (REP quantum restarts can dispatch the same guest
  instruction again); `interp_code_entries` counts dynamic block/continuation entries that executed an instruction;
  `interp_functions` counts distinct analyzed owners with interpreted execution. `interp_unowned_entries` exposes
  entries without an analyzed owner rather than pretending they are functions. A pre-execution quantum transfer
  does not increment execution counters. Per-dispatch owner evidence survives reentrant quantum callbacks.
- Snapshots retain these execution counters in `metrics.execution`; builds preserve/print each input recording's
  interpreted-instruction observation, never a prediction of post-build execution. Old snapshots lacking counters
  report unknown. Successive exact-identity recordings are unioned through the existing list of coverage files.
- Strict code slices remain **function-range granular**, not instruction-level packages. Interior entries in a
  selected owning range are permitted; gaps and unselected functions stop before execution. File-range behavior
  is unchanged. Full workflow, limits and metric definitions: [pipeline.md](../pipeline.md).

Other persistent tests verify:

- **Both widths:** exact finite-program counts (12 instructions, 6 dynamic entries, 2 owners), loop repetition,
  return continuations, zero execution counts on a pre-execution quantum transfer, then correct resumption.
- **Both widths:** owned→unowned straight-line fall-through records only one gap entry; strict execution stops
  before MOV changes EAX. Continued unowned NOPs do not become new entries.
- **AMD64:** nested interpretation during a quantum callback correctly counts both distinct owners.
- **Host:** the real wasm import fills all 1,048,576 slots; duplicates merge kind bits without drops even at capacity;
  real overflow increments drops. Half-open strict range boundaries/gaps are enforced and outside stops recorded.
- **Selection:** interior owning-range/call-closure mapping, `.pdata` precedence, 50,000 disjoint ranges, independent
  enclosing-range-scan agreement on overlapping intervals, union/dedup, module-identity mismatch and overflow rejection.

## Boundaries / porter follow-up

- No private target build or startup replay was performed. Resume the porter on this kit and report the real
  workload's remaining interpreted instructions after every recording/build/reload, with exact module identities.
- Unknown/unowned code is honestly reported and interpreted during discovery; convergence there may require more
  analyzer discovery rather than lifting a falsely attributed preceding function. The finite recording cap is a
  safety net, not proof that every possible workload fits. No hidden automatic cross-reload union or lazy modules.
- Q18 string semantics and Q16 CRT buffering belong to K5a/K5b; this lane does not implement or certify either.
- This new fixture is smaller than `x64-scale` in total instructions but deliberately exceeds the original cap in
  a single function. The full scale fixture retains its own build/browser/oracle gates; no real 7.1M build claim.
- Native BGT examples have no interpreted counterpart: four are oracle N/A, covered by builds/browser tests.
  Physical mobile/Safari/Firefox and native Windows hardware parity are not certified here.
